# Subjects CRUD — Step 10

Implements the existing Lab 04 Subject entity, Lab 05 paths/PUT semantics, and Lab 06
authentication/authorization. No schema or dependency change was required.

## Endpoints and permissions

Base URL: `http://127.0.0.1:3000/api/v1`. Every request requires an Authorization
Bearer token and a currently active account. Existing JWT/role guards and rate limits apply.

| Method | Path | Allowed roles | Success |
|---|---|---|---|
| POST | /subjects | Admin, Department Head | 201 |
| GET | /subjects | All four roles | 200 |
| GET | /subjects/:id | All four roles | 200 |
| PUT | /subjects/:id | Admin, Department Head | 200 |
| DELETE | /subjects/:id | Admin, Department Head | 204, no body |

All four roles means Student, Faculty, Admin, Department Head. Faculty and Students
have read-only access to all Subjects. GET list and PUT preserve Lab 05 methods/paths.

## Validation

POST and PUT accept exactly the following fields. PUT requires ALL four editable
fields; it is a full replacement, not a partial update.

| Field | Rules |
|---|---|
| subjectCode | String, trimmed and uppercased, 1–20 characters; starts with A–Z/0–9; remaining characters A–Z, 0–9, space, underscore, hyphen |
| subjectName | String, trimmed, 1–100 characters, no internal control characters |
| units | Positive JSON integer, maximum 2147483647 (signed INT limit) |
| facultyId | Positive JSON integer, maximum 2147483647; existing active Faculty account |

Unknown fields, including subjectId and actorId, are rejected. Numeric strings, nulls,
booleans, and fractional numbers are not accepted for numeric body fields. Subject IDs
are generated by MariaDB; actor IDs come only from the JWT-verified current account.

`:id` must be a canonical positive decimal integer within the signed INT range.
Zero, negatives, fractions, scientific notation, leading zeros, and text return 400.
A valid ID that does not exist returns 404.

## POST example

```http
POST /api/v1/subjects
Authorization: Bearer <admin-or-head-token>
Content-Type: application/json

{
  "subjectCode": "ITEC116",
  "subjectName": "Systems Integration and Architecture 2",
  "units": 3,
  "facultyId": 3
}
```

Example 201 response (all IDs are illustrative; use actual returned IDs):

```json
{
  "subjectId": 7,
  "subjectCode": "ITEC116",
  "subjectName": "Systems Integration and Architecture 2",
  "units": 3,
  "facultyId": 3
}
```

Creation records SUBJECT_CREATE in the same transaction.

## GET list example and pagination

```http
GET /api/v1/subjects?page=1&pageSize=10
Authorization: Bearer <token-for-any-role>
```

Only `page` and `pageSize` query parameters are supported:

| Parameter | Default | Bounds |
|---|---:|---|
| page | 1 | Integer 1–1000000 |
| pageSize | 10 | Integer 1–100 |

Query strings must contain canonical positive decimal integers. Unknown parameters,
repeated arrays, empty values, fractions, and scientific notation return 400.
Results are ordered by subjectId ascending. No search/filter feature is added.

Schematic 200 response:

```json
{
  "data": [
    {
      "subjectId": 7,
      "subjectCode": "ITEC116",
      "subjectName": "Systems Integration and Architecture 2",
      "units": 3,
      "facultyId": 3
    }
  ],
  "page": 1,
  "pageSize": 10,
  "total": 1,
  "totalPages": 1
}
```

Total describes all Subjects. A valid distant page returns `data: []`, not 404.
An empty table has total/totalPages zero. Concurrent writes can affect offset pages
between requests; this prototype does not provide cross-request snapshot pagination.

## GET individual example

```http
GET /api/v1/subjects/7
Authorization: Bearer <token-for-any-role>
```

Returns 200 with the same five-field Subject object above, or 404.
No Faculty/User relations, names, emails, hashes, or account details are serialized.

## PUT example and academic restrictions

```http
PUT /api/v1/subjects/7
Authorization: Bearer <admin-or-head-token>
Content-Type: application/json

{
  "subjectCode": "ITEC116",
  "subjectName": "Updated Systems Integration",
  "units": 3,
  "facultyId": 3
}
```

Returns 200 with the five-field updated Subject. Successful updates, including a
complete PUT with unchanged values, record SUBJECT_UPDATE with the current actor.

Faculty reassignment returns 409 when ANY Grade belongs to an Enrollment for this
Subject. Other fields may be edited while retaining the same active Faculty. Reassignment
is allowed if Enrollments exist but have no Grades. Every POST/PUT revalidates Faculty.

## DELETE example

```http
DELETE /api/v1/subjects/7
Authorization: Bearer <admin-or-head-token>
```

Success returns 204 with an empty body and records SUBJECT_DELETE. Any Enrollment
blocks deletion, including Dropped/Completed records. The audit keeps the former ID
as contextual metadata; AuditLog.recordId is not an FK to the deleted Subject.

## Error codes

| Code | Meaning |
|---|---|
| 400 | Invalid body/route/query, missing PUT fields, inactive Faculty, or existing user whose role is not Faculty |
| 401 | Missing/invalid/expired JWT or unavailable/inactive authenticated account |
| 403 | Faculty/Student attempts a mutation |
| 404 | Missing Subject or target Faculty ID |
| 409 | Duplicate normalized code, blocked reassignment/deletion, or detected transaction contention |
| 429 | Existing general API rate limit |
| 500 | Unexpected internal failure, including rejected audit insertion; mutation rolled back |

The existing unique index enforces subject code uniqueness, including concurrent
duplicates. Normalization uses uppercase and the database collation is case-insensitive.
Fixed errors never expose SQL, hashes, credentials, request data, or stack traces:

```json
{ "statusCode": 409, "message": "Conflict" }
```

```json
{ "statusCode": 500, "message": "Internal server error" }
```

## Transactional audit logging

Reusable AuditLogsModule exports `AuditLogsService.record(manager, entry)`. It requires
the caller's active transaction manager and never opens another connection. Each successful
mutation stores actor userId, SUBJECT_CREATE/UPDATE/DELETE, tableAffected `subjects`,
recordId, and the database-generated UTC timestamp. Reads and rejected operations do not
create mutation audits. Passwords, tokens, and request bodies are never written to audits.

The business mutation and audit insertion share one TypeORM transaction. An audit
failure propagates and rolls back both. There is no best-effort audit or swallowed error.

PUT/DELETE lock the Subject row for update. Faculty validation takes a shared row lock
against concurrent account changes. Reassignment locks existing Enrollments before
checking Grades, coordinating with Grade→Enrollment FK locks. Subject locks coordinate
with new Enrollment FK checks. Existing restrictive FKs remain the final safeguard.
Deadlocks/timeouts return sanitized 409; callers may retry. Future mutation modules
must preserve these lock/transaction conventions.

## Automated tests and limitations

```powershell
npm.cmd run build
npm.cmd test -- --runInBand
npm.cmd run test:e2e -- --runInBand
npm.cmd run test:database
```

Subjects tests create temporary Users, Subjects, Enrollments, and a Grade in an outer
uncommitted transaction. User/Subject repository overrides bind the tested services to
that transaction. Real service transactions use MariaDB savepoints, allowing mutation
and audit rollback tests while preserving fixtures. Every test rolls back, closes its
application, and checks temporary rows are absent. Seeded accounts/data are never updated;
the demo credential file is checked unchanged. AUTO_INCREMENT gaps are expected.

Tests cover both mutating roles, all-role reads, JWT/403 rejection, duplicates, DTO/PUT/
query/ID validation, Faculty eligibility, missing IDs, academic restrictions, pagination,
audit actor/action records, actual database rejection of audit INSERTs, rollback after
an audit has been inserted, and confidential-data exclusion. Fault injection uses Jest
spies only; no production testing flag or endpoint was added.

Verified results: build passed; 80 Subjects HTTP tests and all 31 existing authentication
HTTP tests passed (111 combined); 2 configuration unit tests and all 47 database checks
passed. Reference PDF hashes, the approved schema, and demo passwords are unchanged.

No other CRUD API, frontend, schema migration, or dependency upgrade was introduced.
Single-department scope, local HTTP, process-local rate limits, and the previously
confirmed Windows Application Control/lint limitation remain. See
[authentication security](authentication-security.md) and [database design](database-design.md).
