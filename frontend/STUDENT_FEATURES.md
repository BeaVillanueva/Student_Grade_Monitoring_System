# Step 14.10 — Student workspace

Implemented and locally verified on 26 November 2026. Login at
http://127.0.0.1:5173/login. No backend or database changes were made.

## Pages and behavior

| Route | Functionality |
| --- | --- |
| `/student` | Unique own subjects, recorded grades and Pending inquiry totals; grade/inquiry status counts; personal grades table; refresh and functional quick actions |
| `/student/subjects` | Own enrollment rows with subject code/name, units, semester, school year, status, enrollment date, Faculty ID fallback and details |
| `/student/grades` | Enrollment-grouped Midterm/Final records, individual grade IDs, scores, remarks, recording dates, details and grade-linked inquiry actions |
| `/student/grade-inquiries` | Own inquiries, related subject/grade/score, message, status, submission and resolution information, details and inquiry submission |
| `/student/profile` | Existing verified own profile |

Subjects derive exclusively from the authenticated Student's own enrollments.
The backend scopes enrollments, grades and inquiries; the frontend also rejects
unexpected foreign enrollment ownership and inconsistent grade/inquiry links.
The all-subjects endpoint is permitted, but only subjects referenced by own
enrollments reach the Student feature dataset and selectors. The dashboard
counts unique subject IDs, while tables preserve separate enrollment IDs across
terms. These two counts are explicitly distinguished.

Grades group by enrollment ID, preserving individual Midterm/Final grade IDs.
Missing grades display **Not recorded**, never zero. Existing decimal strings,
date-only enrollment dates and shared timestamp formatting are preserved. No
GPA, averages, passing status or invented academic policy is calculated.

Search, school-year/semester/subject/grade-type filters and inquiry status filters
are clearly labeled client-side operations across complete personal datasets.
Pagination is client-side; no unsupported filters are sent to the backend.
Complete loading retains the existing 100-page, 100-record-per-page bound and
bounded scheduler. Incomplete/error results do not become partial global totals.

## Inquiry submission and permissions

The form selects an own subject, an existing own grade and a message. Opening it
from a grade preselects the corresponding record. Each grade option identifies
the grade type, exact score, grade ID, enrollment ID and academic term.
`POST /grade-inquiries` sends exactly `gradeId` and `message`. The existing strict
Zod contract enforces a nonempty trimmed message, at most 4000 Unicode characters,
at most 16000 UTF-8 bytes, and no NUL. No Student ID, status, resolver or timestamp
fields are submitted. Confirmation and the shared duplicate-submit guard precede
the mutation; successful submission invalidates inquiry/dashboard data and
refreshes the workspace. Backend errors are sanitized.

Multiple inquiries about an existing grade remain allowed because the backend
does not prohibit them. There are no Student controls for resolving, editing,
deleting or reopening inquiries, or mutating grades, subjects or enrollments.
Messages and resolution notes render as plain React text. Faculty and resolver
names are not discovered through forbidden requests: Faculty IDs and unavailable
resolver identifiers are shown where names are unavailable. No general users
list or individual user-detail requests are generated by Student academic pages.

The implementation reuses the shell, role guards, API services, schemas,
EntityForm, confirmations, tables, pagination, filters, feedback states, summary
cards, status badges, toast notifications, reference presentation and date
utilities. Private cache keys remain session-scoped with cancellation and cache
clearing on identity changes. Backend authorization remains authoritative.

## Limitations and handoff

Inquiry submission was tested with offline fixtures only; live verification was
read-only. Large complete datasets can wait for the existing budget or hit the
safety bound. The permitted all-subject catalog remains session-cached, while
Student views/selectors expose only enrollment-associated subjects. Local HTTP
and memory-only session/reload limitations remain unchanged.

New files: `src/features/student/student-data.ts`, `student-queries.ts`,
`student-page.tsx`, `test/student.test.ts` and this report. Routing and README were
updated; existing feature source, dependencies, lockfile and Vite configuration
were preserved. No backend, database, credential, security-policy or Postman
changes were made. No commit or push was performed. Both servers remain running.
